## six source-derived edges

all findings below are VERIFIED by source trace, not yet runtime evidence.

### 1. outer argument copy fails before the callee

`IdMapWrapper::add(MappedType)` takes its argument by value
(`source/core/StarIdMap.hpp:108`). copying an existing lvalue into that parameter
must finish before the body calls `nextId`. an injected copy failure therefore
preserves cursor 10 and the existing key 12/value 7; the next explicit `nextId`
returns 10. the original local payload remains 9. a unique exception identity
token and construction/destruction conservation are checked.

this differs from the accepted baseline's inner argument-copy failure:
`StarIdMap.hpp:109–110` calls `nextId` before passing the named mapped parameter
to the by-value `MapMixin::insert` (`StarMap.hpp:261`), so that later failure has
already advanced the cursor. the outer case does not establish a universal
rollback guarantee. no base insertion starts at all.

the payload remains copyable, with a potentially throwing move constructor, so
flat hash bucket/vector growth may copy it. the baseline already falsified a
broader hash move-only assumption; this edge does not reopen it. no exact
container-dependent copy/move count is golden. only the one attempted OUTER
copy, its exception identity and conservation are constrained.

### 2. duplicate serialized keys retain the first value

`DataStream::readMapContainer` clears the base container, then calls its ordinary
`insert` for each decoded pair (`source/core/StarDataStream.hpp:354–363`). it
does not call `IdMapWrapper::add` and does not inspect the insertion-result bool.
raw packet:

```text
02 0000000b 0000004d 0000000b 00000063 0000000a 0000000c 0000000a
```

count two, key 11/value 77 then key 11/value 99, range 10..12, cursor 10.
both entries and metadata are consumed, no IdMap duplicate exception is thrown,
and the resulting map has size one, value 77, next id 10. this does not impose
multi-entry serialization order on the hash container: the INPUT order is fixed,
and no unordered multi-entry output is golden.

### 3. an absent out-of-range loaded cursor is returned first

stream extraction directly loads metadata (`StarIdMap.hpp:131–136`), without
normalizing the cursor. raw packet:

```text
00 0000000a 0000000c 00000063
```

`nextId` checks occupancy before calling `cycleIncrement` for the stored cursor
(`StarIdMap.hpp:94–98`). cursor 99 is absent, so the first return is 99; only its
subsequent increment normalizes to minimum 10. the next return is 10. neither
call reserves an entry. source: `StarMathCommon.hpp:318–323`. no validation or
bug fix is added.

### 4. a partial primitive read overwrites bytes before EOF

this edge is deliberately native-profile-specific. compilation requires
`STAR_LITTLE_ENDIAN`, and main independently checks the host's object-byte order.
the stream still uses its default BIG-endian primitive encoding; host endianness
and wire endianness are different contracts.

start with uint32 range `0x11223344..0x55667788`, one existing entry and one
`nextId` call, leaving cursor `0x11223345`. read ONLY bytes `00 01 02`:
count zero, then two bytes of the four-byte minimum.

mechanism:

- `readMapContainer` clears the old entry and consumes count zero.
- uint32 extraction passes existing scalar storage to `readData` BEFORE calling
  `fromByteOrder` (`source/core/StarDataStream.cpp:238–241`).
- `DataStreamBuffer::readData` calls `Buffer::readFull`
  (`StarDataStreamDevices.cpp:125–127`).
- `Buffer::doRead` copies the available two bytes via `memcpy`
  (`StarBuffer.cpp:249–261`); `Buffer::read` advances its position by two
  (`StarBuffer.cpp:138–141`).
- `IODevice::readFull` throws `EofException` after that short read
  (`StarIODevice.cpp:54–61`). uint32 extraction never reaches endian conversion.

little-endian minimum storage starts `44 33 22 11`, becomes `01 02 22 11`, and
therefore represents `0x11220201`. maximum and cursor are untouched. the empty
map's post-failure serialization MUST be:

```text
00 11220201 55667788 11223345
```

stream position is 3. the exact EOF dynamic type is checked; there is no invented
rollback, zero-fill or conversion-on-failure. unsigned object-byte modification
is defined for these literals; a big-endian host needs a different diagnostic,
not a changed golden. this is not a general cross-platform malformed-stream
promise or evidence for every partial field/stream implementation.

### 5. printable uint8 duplicate messages print a character

explicit id 65 in uint8 range 64..67 is added twice. `StarIdMap.hpp:104` uses
`outputAny(id)`. its ostream wrapper (`StarOutputProxy.hpp:30–35`) forwards the
actual unsigned character type, so on this admitted ASCII native profile the
exact `what()` string is:

```text
(IdMapException) IdMapWrapper::add(id, value) called with pre-existing id 'A'
```

not decimal `'65'`. dynamic type remains exactly `IdMapException`; the first
value is retained. `StarException_unix.cpp:78–86` explains the type prefix. this
uint8 case never fills the id domain or invokes a problematic full-domain scan.

### 6. outside explicit keys count toward exhaustion

explicit insertion performs no range check (`StarIdMap.hpp:102–105`). keys
99, 100, 101 in range 10..12 create size three. the original fullness comparison
is `uint32(size) > max - min`, so `3 > 2` throws even though 10, 11, 12 are all
free. dynamic type is exactly `IdMapException`, with exact `what()`:

```text
(IdMapException) No id space left in IdMapWrapper
```

this preserves a source behavior, not a cleaned-up allocation algorithm.
